# Архитектура «Сноски»

Документ фиксирует устройство системы и решения, принятые на вехе 1. Каждое решение — с причиной; при изменении решения раздел обновляется в том же изменении.

## Слои и корень композиции

Бэкенд — один Python-пакет `snoska`, разделённый по слоям; внутри слоя код разложен по контекстам (`tenancy`, `documents`, `corpus`).

| Слой | Что внутри | Зависит от |
| --- | --- | --- |
| `domain` | сущности, инварианты, реестры (роли, форматы, виды документов), правила (реквизиты, ссылки на нормы) | ни от чего |
| `ports` | протоколы репозиториев, unit of work, хранилища, очереди, парсеров, OCR, моделей, источников корпуса, identity | `domain` |
| `application` | сценарии: загрузка, разбор, запросы, синхронизация и эмбеддинги корпуса, доступ | `ports`, `domain` |
| `infrastructure` | адаптеры к PostgreSQL, Redis/Dramatiq, python-docx, pdfplumber, Tesseract, Ollama, OpenAI-совместимому API, Keycloak, pravo.gov.ru | всё внутреннее |
| `bootstrap` | настройки и `build_container` — единственное место, где адаптеры связываются со сценариями | всё |
| `api`, `worker`, `cli` | точки входа | `bootstrap` |

Направление зависимостей и «чистоту» домена (никаких SQLAlchemy, FastAPI, httpx в `domain`; никаких фреймворков в `application`) проверяет `import-linter` в гейте.

## Тенанты, роли и изоляция

**Источник истины об участниках — Keycloak.** В realm `snoska` включены организации (Keycloak 26.8). У каждой организации — группы `owner`, `lawyer`, `executor`, `observer`, каждой группе назначена одноимённая клиентская роль `snoska-api`. Маппер «Organization Group Membership» с ролями кладёт в токен роли *по организациям*:

```json
"organization": {
  "polyarnaya-zvezda": {
    "id": "5ce1…",
    "resource_access": { "snoska-api": { "roles": ["lawyer"] } }
  }
}
```

Так один человек может состоять в нескольких организациях с разными ролями, а роль меняется в одном месте. Права ролей — реестр в домене (`ORGANIZATION_ROLES`); код проверяет права (`documents.upload`), а не названия ролей. Неизвестные роли игнорируются.

**Запись тенанта в платформе** создаётся при первом обращении участника организации (имя берётся из Keycloak сервисным аккаунтом `snoska-directory`), вместе с пространством по умолчанию — в одной транзакции, идемпотентно (`ON CONFLICT DO NOTHING`).

**Изоляция обеспечивается базой, а не только кодом:**

- миграции выполняет роль-владелец `snoska_owner`, приложение работает ролью `snoska_app` без `BYPASSRLS` и без владения таблицами;
- на всех таблицах с данными тенанта — политика RLS `organization_id = current_setting('snoska.tenant_id')`; unit of work выставляет настройку `set_config(…, true)` — она живёт только до конца транзакции и не «протекает» в пул соединений;
- внешние ключи составные (`(document_id, organization_id)` → `documents(id, organization_id)`), строка не может сослаться на чужого тенанта даже при ошибке в коде;
- без контекста тенанта строки тенантов не видны вовсе.

Тесты `tests/integration/test_tenant_isolation.py` проверяют это на настоящем PostgreSQL: чужие строки не видны запросам, запись в чужого тенанта отклоняется базой, роль приложения не может обойти RLS, API не пересекает тенанты и проверяет роли.

## Документы

1. **Загрузка** — потоком: формат определяется по расширению *и* сигнатуре файла (реестр форматов), размер ограничен и в middleware (включая chunked-запросы), и при записи в хранилище. Повторный запрос с тем же `Idempotency-Key` возвращает первый результат (уникальный ключ в БД). Оригиналы — в хранилище за портом `BlobStorage`; сейчас у него адаптер файловой системы, объектное хранилище — см. «Принятые решения».
2. **Транзакционный outbox.** Документ, версия и задание на разбор записываются одной транзакцией. Триггер шлёт `NOTIFY`, ретранслятор в процессе воркера сразу забирает сообщения (`FOR UPDATE SKIP LOCKED`, безопасно для нескольких экземпляров) и передаёт в очередь; периодический опрос подстраховывает. Доставка «хотя бы один раз», обработчики идемпотентны.
3. **Разбор** — в воркере, с ограничением одновременности и ретраями; повреждённый файл фиксируется как окончательная ошибка со стабильным кодом, сбой инфраструктуры — повторяется, на последней попытке тоже фиксируется.
   - DOCX: эффективное оформление по цепочке стилей (`basedOn` → умолчания документа, темы шрифтов), нумерация списков Word в том виде, как её видит читатель («1.2.», «а)», «•»), таблицы с объединениями, поля разделов.
   - PDF: строки текстового слоя собираются в абзацы по геометрии (отступы, интервалы, короткие строки, нумерация), таблицы с линейками, колонтитулы и номера страниц отбрасываются, поля страниц измеряются по тексту.
   - Скан: страницы без текстового слоя рендерятся (pypdfium2) и распознаются Tesseract (`rus+eng`); уверенность распознавания сохраняется на уровне блока.
4. **Реквизиты** (наименование организации, вид и дата документа, номер, место, грифы, заголовок, подпись и др.) — правила домена, применяемые к блокам *при чтении*: улучшенное правило сразу действует на все сохранённые версии. Шапка и зона подписи ограничены началом и концом нумерованной части документа.

## Корпус норм

- **Источник** — «Законодательство России» на официальном портале pravo.gov.ru (`pravo_ips`): берётся текущая редакция (номер редакции, список изменяющих законов). Снимок страницы портала входит в репозиторий для воспроизводимого развёртывания без сети (`snapshot`); синхронизация из снимка и с портала даёт одну и ту же редакцию.
- **Структура** — глава → статья → часть → пункт → подпункт; надстрочные номера (`18¹`) становятся `18.1`; редакционные пометки отделены от текста нормы; утратившие силу положения помечены и не попадают в поиск. У каждой единицы — устойчивый якорь (`st-18.1/ch-1/p-2`) и ссылка в принятом порядке («п. 2 ч. 1 ст. 18.1 152-ФЗ»).
- **Редакции неизменяемы.** Совпадение определяется хешем нормативного содержания; новая редакция активируется только после того, как все её фрагменты получили векторы — поиск никогда не видит частично проиндексированную редакцию.
- **Эмбеддинги** хранятся по хешу фрагмента в пространстве (`bge-m3`, 1024): неизменённый текст между редакциями не пересчитывается. Фрагмент для поиска самодостаточен: ссылка, заголовок статьи, вводные слова родительских частей и текст. Индекс — частичный HNSW по пространству; новое пространство добавляется миграцией.
- **Обновление**: `snoska corpus sync --source pravo_ips` загружает текущую редакцию с портала, `snoska corpus snapshot` обновляет снимок. Плановая проверка — см. «Принятые решения».

## Принятые решения (реализация — веха 3)

**Хранилище файлов — объектное, за портом.** Порт объектного хранилища (запись потоком, чтение потоком, удаление, временная ссылка на скачивание) заменяет нынешний `BlobStorage`. Адаптеры:

- **MinIO** — S3-совместимое хранилище, разворачивается у себя (сервис в Docker Compose и в конфигурации деплоя); используется в демо и в продакшене. Работа идёт по протоколу S3, поэтому облачное S3-совместимое хранилище подключается настройкой того же адаптера.
- **Локальная файловая система** — для разработки и тестов.

Ключи объектов остаются как сейчас (`tenants/{организация}/documents/{документ}/versions/{версия}`): изоляция тенантов видна и на уровне хранилища, а переход между адаптерами не меняет данные в БД.

**Обновление корпуса — плановая проверка раз в неделю.** Воркер по расписанию запрашивает у портала текущую редакцию 152-ФЗ. Если хеш нормативного содержания изменился, создаётся новая редакция: она проходит эмбеддинги и активируется по уже действующему правилу (только целиком). Администратор платформы получает уведомление: что изменилось (номер редакции, изменяющие законы, затронутые статьи) и что редакция активирована. Неудачная проверка (портал недоступен, разметка изменилась) — тоже уведомление, текущая редакция остаётся в работе. Расписание и получатели задаются настройками; ручной запуск — та же команда `snoska corpus sync`.

## Выбор технологий

**Очередь — Dramatiq + Redis.** Зрелая библиотека с надёжной доставкой (подтверждения, возврат незавершённых сообщений), ретраями с backoff, лимитами времени, middleware и асинхронными акторами. Celery тяжелее и слабее в asyncio; Arq в режиме поддержки; Taskiq моложе. Лицензия LGPL-3.0 — библиотека используется без изменений.

**PDF — pdfplumber (pdfminer.six) + pypdfium2 + Tesseract.** Даёт символы со шрифтами, кеглем и координатами — то, что нужно для проверок оформления на вехе 2, — а pypdfium2 быстро рендерит страницы для OCR. Docling тянет PyTorch и модели на гигабайты и неуместен при ограниченной памяти; его сильные стороны (layout-модели) покрываются эвристиками, которые мы контролируем.

**Языковая модель — `qwen3.5:9b`** (Apache-2.0): сильный русский, 256K контекста, 6,6 ГБ в Q4 — помещается в 8 ГБ видеопамяти. **Эмбеддинги — `bge-m3`** (MIT): мультиязычная модель с хорошим качеством поиска на русском, 1024 измерения, 8K токенов. Обе — за портами `LanguageModel` и `Embedder`; для продакшена есть адаптер к OpenAI-совместимому API, выбор — настройкой `SNOSKA_AI_PROVIDER`. Ollama 0.20 не применяет ограничение по JSON-схеме при отключённом «размышлении», поэтому адаптер использует JSON-режим, передаёт схему в системном сообщении и проверяет ответ.

**Аутентификация — Keycloak, вход через сервер приложения (BFF).** Authorization Code + PKCE выполняет Next.js на сервере; токены хранятся в зашифрованной серверной сессии в Redis и не попадают в браузер; браузер обращается к API только через маршрут `/bff`, который подставляет токен. API проверяет подпись (JWKS с кешем по `kid`), издателя, аудиторию и срок действия.

## Фронтенд

Next.js 16 (App Router), TypeScript strict. Типы API генерируются из `backend/openapi.json` — ручных копий контрактов нет. Списки и документ рендерятся на сервере с первыми данными и продолжаются на клиенте (TanStack Query, гидрация). Собственная дизайн-система: токены (цвета для обеих тем объявлены один раз через `light-dark()`), компоненты на примитивах Radix, иконки Tabler; Stylelint запрещает литералы цветов и отступов вне токенов. Все тексты — в `messages/ru.json` (next-intl).

## Наблюдаемость

Структурные JSON-логи (structlog) с `request_id`, пользователем, тенантом и `trace_id`; метрики Prometheus (`/api/metrics`, у воркера — порт 46302): запросы, задержки, задания и их длительность; трассировка OpenTelemetry включается настройкой (`SNOSKA_TRACING_EXPORTER=otlp`). Ошибки API — RFC 9457 с устойчивым `code`.
