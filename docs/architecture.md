# Архитектура «Сноски»

Документ фиксирует устройство системы и решения, принятые на вехах 1–3. Каждое решение — с причиной; при изменении решения раздел обновляется в том же изменении.

## Слои и корень композиции

Бэкенд — один Python-пакет `snoska`, разделённый по слоям; внутри слоя код разложен по контекстам (`tenancy`, `documents`, `corpus`, `checks`).

| Слой | Что внутри | Зависит от |
| --- | --- | --- |
| `domain` | сущности, инварианты, реестры (роли, форматы, виды документов), правила (реквизиты, ссылки на нормы) | ни от чего |
| `ports` | протоколы репозиториев, unit of work, хранилища, очереди, парсеров, OCR, моделей, источников корпуса, identity | `domain` |
| `application` | сценарии: загрузка, разбор, запросы, синхронизация и эмбеддинги корпуса, доступ | `ports`, `domain` |
| `infrastructure` | адаптеры к PostgreSQL, Redis/Dramatiq, python-docx, pdfplumber, Tesseract, OpenAI-совместимому API моделей, Keycloak, pravo.gov.ru; загрузка реестра проверок | всё внутреннее |
| `bootstrap` | настройки и `build_container` — единственное место, где адаптеры связываются со сценариями | всё |
| `api`, `worker`, `cli` | точки входа | `bootstrap` |

Направление зависимостей и «чистоту» домена (никаких SQLAlchemy, FastAPI, httpx в `domain`; никаких фреймворков в `application`) проверяет `import-linter` в гейте.

## Тенанты, роли и изоляция

**Источник истины об участниках — Keycloak.** В realm `snoska` включены организации (Keycloak 26.8). У каждой организации — группы `owner`, `lawyer`, `executor`, `observer`, каждой группе назначена одноимённая клиентская роль `snoska-api`. Маппер «Organization Group Membership» с ролями кладёт в токен роли *по организациям*:

```json
"organization": {
  "polyarnaya-zvezda": {
    "id": "5ce1…",
    "resource_access": { "snoska-api": { "roles": ["lawyer"] } }
  }
}
```

Так один человек может состоять в нескольких организациях с разными ролями, а роль меняется в одном месте. Права ролей — реестр в домене (`ORGANIZATION_ROLES`); код проверяет права (`documents.upload`), а не названия ролей. Неизвестные роли игнорируются.

**Запись тенанта в платформе** создаётся при первом обращении участника организации (имя берётся из Keycloak сервисным аккаунтом `snoska-directory`), вместе с пространством по умолчанию — в одной транзакции, идемпотентно (`ON CONFLICT DO NOTHING`).

**Изоляция обеспечивается базой, а не только кодом:**

- миграции выполняет роль-владелец `snoska_owner`, приложение работает ролью `snoska_app` без `BYPASSRLS` и без владения таблицами;
- на всех таблицах с данными тенанта — политика RLS `organization_id = current_setting('snoska.tenant_id')`; unit of work выставляет настройку `set_config(…, true)` — она живёт только до конца транзакции и не «протекает» в пул соединений;
- внешние ключи составные (`(document_id, organization_id)` → `documents(id, organization_id)`), строка не может сослаться на чужого тенанта даже при ошибке в коде;
- без контекста тенанта строки тенантов не видны вовсе.

Тесты `tests/integration/test_tenant_isolation.py` проверяют это на настоящем PostgreSQL: чужие строки не видны запросам, запись в чужого тенанта отклоняется базой, роль приложения не может обойти RLS, API не пересекает тенанты и проверяет роли.

## Документы

1. **Загрузка** — потоком: формат определяется по расширению *и* сигнатуре файла (реестр форматов), размер ограничен и в middleware (включая chunked-запросы), и при записи в хранилище. Повторный запрос с тем же `Idempotency-Key` возвращает первый результат (уникальный ключ в БД). Оригиналы — в хранилище за портом `BlobStorage` (см. «Хранилище файлов»).
2. **Транзакционный outbox.** Документ, версия и задание на разбор записываются одной транзакцией. Триггер шлёт `NOTIFY`, ретранслятор в процессе воркера сразу забирает сообщения (`FOR UPDATE SKIP LOCKED`, безопасно для нескольких экземпляров) и передаёт в очередь; периодический опрос подстраховывает. Доставка «хотя бы один раз», обработчики идемпотентны.
3. **Разбор** — в воркере, с ограничением одновременности и ретраями; повреждённый файл фиксируется как окончательная ошибка со стабильным кодом, сбой инфраструктуры — повторяется, на последней попытке тоже фиксируется.
   - DOCX: эффективное оформление по цепочке стилей (`basedOn` → умолчания документа, темы шрифтов), нумерация списков Word в том виде, как её видит читатель («1.2.», «а)», «•»), таблицы с объединениями, поля разделов.
   - PDF: строки текстового слоя собираются в абзацы по геометрии (отступы, интервалы, короткие строки, нумерация), таблицы с линейками, колонтитулы и номера страниц отбрасываются, поля страниц измеряются по тексту.
   - Скан: страницы без текстового слоя рендерятся (pypdfium2) и распознаются Tesseract (`rus+eng`); уверенность распознавания сохраняется на уровне блока.
4. **Реквизиты** (наименование организации, вид и дата документа, номер, место, грифы, заголовок, подпись и др.) — правила домена, применяемые к блокам *при чтении*: улучшенное правило сразу действует на все сохранённые версии. Шапка и зона подписи ограничены началом и концом нумерованной части документа.

## Корпус норм

- **Источник** — «Законодательство России» на официальном портале pravo.gov.ru (`pravo_ips`): берётся текущая редакция (номер редакции, список изменяющих законов). Снимок страницы портала входит в репозиторий для воспроизводимого развёртывания без сети (`snapshot`); синхронизация из снимка и с портала даёт одну и ту же редакцию.
- **Структура** — глава → статья → часть → пункт → подпункт; надстрочные номера (`18¹`) становятся `18.1`; редакционные пометки отделены от текста нормы; утратившие силу положения помечены и не попадают в поиск. У каждой единицы — устойчивый якорь (`st-18.1/ch-1/p-2`) и ссылка в принятом порядке («п. 2 ч. 1 ст. 18.1 152-ФЗ»).
- **Редакции неизменяемы.** Совпадение определяется хешем нормативного содержания. Новая редакция вступает в силу сразу при загрузке: текст и цитаты доступны независимо от модели эмбеддингов.
- **Поиск — по пространствам эмбеддингов.** Пространство — это модель эмбеддингов и размер её векторов из конфигурации (`SNOSKA_EMBEDDING_MODEL`, `SNOSKA_EMBEDDING_DIMENSIONS`); векторы разных моделей никогда не сравниваются. Редакция доступна поиску в пространстве только когда все её фрагменты получили там векторы (`edition_indexes`): поиск никогда не видит частично проиндексированную редакцию и честно отвечает `corpus_not_indexed`, пока индекса нет.
- **Смена модели — одной командой** `snoska corpus reindex` (`make index`): регистрирует пространство и его частичный HNSW-индекс (как владелец схемы; векторы больше 2000 измерений индексируются как `halfvec`), досчитывает недостающие векторы и отмечает редакции готовыми; `--prune` удаляет векторы и индексы прежних моделей. Векторы хранятся по хешу фрагмента: неизменённый текст между редакциями не пересчитывается. Фрагмент для поиска самодостаточен: ссылка, заголовок статьи, вводные слова родительских частей и текст.
- **Обновление**: `snoska corpus sync --source pravo_ips` загружает текущую редакцию с портала, `snoska corpus snapshot` обновляет снимок. Плановая проверка новой редакции — см. «Операции платформы».

## Хранилище файлов

Порт `BlobStorage` (запись потоком с лимитом размера и SHA-256, чтение, поток, удаление, проверка наличия) и два адаптера: **MinIO/S3** (`S3BlobStorage`, официальный SDK `minio` в рабочих потоках; загрузка сперва буферизуется во временный файл, поэтому лимит и хеш проверяются до появления объекта) и **файловая система** (разработка и тесты). Выбор — настройкой `SNOSKA_STORAGE_BACKEND`; ключи объектов не зависят от адаптера (`tenants/{организация}/documents/{документ}/versions/{версия}`), поэтому `snoska storage copy-to-s3` переносит файлы без изменений в БД. MinIO — сервис Docker Compose (порты 46340 и консоль 46341); образ — `chainguard/minio`: официальные образы MinIO больше не публикуются в Docker Hub и Quay. Контрактный тест прогоняет один набор проверок на обоих адаптерах (S3 — против настоящего MinIO в CI). Доступность хранилища входит в состояние системы.

## Администрирование организации

- **Участники и роли — в Keycloak.** Порт `OrganizationDirectory` (список, приглашение с письмом о входе, смена роли, удаление); адаптер работает с организациями и группами ролей Keycloak через сервисную учётную запись. Инвариант домена — в организации всегда остаётся владелец (`last_owner`). Роли и их права — реестр домена; экраны берут список из `/v1/administration/catalog` (роли, области API-ключей, события вебхуков, разделы журнала), ничего не перечисляя в коде.
- **Пространства и роли в них.** Пространство открытое (участники работают с ролью организации) или закрытое (видят только перечисленные). Роль в пространстве заменяет роль организации внутри него — в обе стороны: наблюдатель организации может быть юристом в «Кадрах». Правило — одна функция домена (`workspace_access`); `WorkspaceGate` применяет его к каждому запросу документа, закрытое пространство для постороннего — 404, а не 403. API отдаёт итоговые права вместе с пространством и документом, и интерфейс показывает действия по ним, а не по роли в организации.
- **Журнал аудита** — таблица только на добавление (роль приложения: `SELECT, INSERT`), запись — в транзакции действия, поэтому журнал не расходится с данными. Кто (человек, API-ключ или система — с именем на момент действия), что (код действия), над чем и подробности. Фильтр по разделу, автору и периоду, курсорная пагинация, экспорт CSV с теми же фильтрами (UTF-8 с BOM для Excel, защита от формул в ячейках).

## Интеграции

- **API-ключи** — токен `snk_…` показывается один раз; хранится префикс для поиска и SHA-256 токена. У ключа — области (`documents:read`, `documents:write`, `checks:run`, `audit:read`), они превращаются в права той же модели доступа, что у людей; запрос с ключом — актор `api_key` в журнале. Отзыв действует немедленно.
- **Вебхуки** — события организации (`document.uploaded`, `document.parsed`, `check.completed`, `check.failed`, `finding.reviewed`) записываются в outbox в транзакции события, доставка — отдельной задачей. Тело подписано HMAC-SHA256 секретом точки (`Snoska-Signature: t=…,v1=…`, метка времени входит в подпись), секрет хранится зашифрованным и показывается один раз (при создании и выпуске нового). Повторы — с растущей паузой до шести попыток; журнал доставок хранит статус, код ответа, время ответа и следующую попытку, доставку можно повторить вручную. Адаптер HTTP не ходит во внутренние адреса (защита от SSRF) — на демо-стенде это разрешено настройкой ради встроенного приёмника, который проверяет подпись как настоящая интеграция.

## Тарифы и использование

- **Тарифы — данные** (`backend/data/billing/plans.yaml`): цена в копейках и лимиты месяца по метрикам (страницы, проверки, вопросы к норме, исправления оформления, участники). Новый тариф — новая запись.
- **Леджер** — проводки в целых единицах, у каждой причина (`check_run`, `autofix`, `question`) и ссылка на объект. Страница DOCX — 1 800 знаков текста (лист при кегле 14), PDF — его страницы.
- **Лимит проверяется на сервере атомарно**: списание берёт блокировку строки подписки и в той же транзакции сверяет сумму месяца с лимитом; превышение — `402 quota_exceeded`, параллельные запросы не проходят оба (это проверяет интеграционный тест). Проверка новой версии, не прошедшая по лимиту, фиксируется как запуск с кодом `quota_exceeded`, и экран ведёт к тарифу.
- **Смена тарифа**: дешевле — со следующего месяца; дороже — счёт и платёж у провайдера, тариф меняется по его уведомлению. **Провайдер оплаты — за портом**; сейчас есть тестовый провайдер: подписанная ссылка на собственную страницу оплаты (`/pay/test/…`, вне приложения, с пометкой тестового режима), решение «оплатить/отклонить» приходит обратно подписанным уведомлением через outbox, как у настоящего. Обработка уведомления идемпотентна по идентификатору события (`payment_events`). Подключение настоящего провайдера — новый адаптер порта, выбор провайдера за владельцем.

## Автоисправление оформления

Исправляются только детерминированные правила оформления и только в DOCX: поля, кегль, интервал, абзацный отступ, формат дат. План строится в домене из замечаний (у каждого правила — свой планировщик; чего нельзя безопасно поправить, остаётся с причиной: нужен человек, юридическое замечание, файл не редактируется, правка небезопасна). Патчер обходит те же блоки, что парсер, поэтому номера блоков совпадают, а замена текста учитывает разбиение на фрагменты оформления. Результат — **новая версия** (происхождение `autofix`, ссылка на исходную), оригинал не трогается; новая версия разбирается и проверяется как загрузка. Журнал «что изменено» — строки с мерой (поля, кегль, интервал, отступ, текст), значениями «было/стало» и числом затронутых абзацев; экран сравнения показывает их с единицами и ведёт к месту в тексте. Исправление расходует лимит «исправления оформления».

## «Спросить норму»

Вопрос — поиск ближайших положений действующей редакции (по эмбеддингам, как в юридических проверках) и запрос к модели за портом `LanguageModel`: ответ по JSON-схеме — нашёлся ли ответ, текст со сносками `[n]`, для каждой сноски — ключ положения и дословная цитата. Ответ принимается, только если каждая цитата дословно есть в тексте названного положения; иначе модель получает ошибку и пробует снова, после трёх попыток — честное «в норме не найдено». Ссылку на пункт пишет корпус, а не модель. Без настроенного API — `503 model_not_configured`, без индекса — `409 corpus_not_indexed`; экран показывает это состояние и шаги для администратора. Разговоры хранятся по организации и автору; вопрос расходует лимит «вопросы к норме».

## Операции платформы

- **Плановые задачи** — таблица `task_states` (следующий запуск задачи); воркер раз в минуту забирает наступившие с `FOR UPDATE SKIP LOCKED`, поэтому при нескольких экземплярах задача выполняется один раз.
- **Проверка новой редакции 152-ФЗ — раз в неделю** (`SNOSKA_CORPUS_WATCH_INTERVAL_HOURS`, ручной запуск — `snoska corpus watch` или кнопка в консоли). Портал опрашивается за портом источника корпуса; новая редакция сохраняется и вступает в силу по обычному правилу, индексируется для поиска целиком. Каждая проверка записывается (`edition_checks`); о новой редакции и о неудачной проверке администраторы платформы (роль realm `platform-admin`) получают письмо через SMTP — на стенде это Mailpit.
- **Консоль оператора** (`/platform`): организации с тарифом и использованием месяца (оператор может сразу перевести организацию на другой тариф — с записью в её журнал), тарифы, состояние системы — службы (база, хранилище, очередь, вход), модели, корпус и его индекс, проверки редакции, следующая проверка, очередь outbox.

## Проверки

**Реестр проверок — данные** (`backend/data/checks/*.yaml`). Запись описывает проверку целиком: виды документов, к которым она применима; норму (пункт ГОСТ Р 7.0.97-2016 или якоря положений 152-ФЗ в корпусе); серьёзность по умолчанию; способ — детерминированное правило с параметрами или вопрос к языковой модели (`brief`: что спросить, что считать выполнением, что искать в документе). Новая проверка — новая запись, движок не меняется; новое детерминированное правило — новая стратегия в реестре правил. Реестр проверяется при загрузке (правило существует и принимает параметры, виды документов зарегистрированы), его ревизия — хеш файлов; каждый запуск хранит ревизию, с которой он выполнен.

**Детерминированные проверки оформления** — чистые правила домена над разобранной структурой: поля, кегль, интервал, абзацный отступ, реквизиты, подпись, даты, нумерация. Требования стандарта сформулированы своими словами со ссылкой на пункт; текст стандарта не распространяется. Где данных нет (скан без шрифтов), правило отвечает «неприменимо», а не угадывает.

**Юридические проверки 152-ФЗ — только с опорой.** Для требования находятся фрагменты документа (поиск по эмбеддингам с бонусом за ключевые слова, таблицы — построчно) и положения закона из действующей редакции корпуса: названные в реестре и ближайшее по смыслу. Модель отвечает JSON-объектом по схеме: вердикт (`present`, `partial`, `absent`, `uncertain`), цитаты из фрагментов, номер положения из данных ей. Ответ принимается, только если каждая цитата дословно находится в тексте документа (с точностью до регистра, пробелов и вида кавычек) и положение — одно из данных; цитату нормы в замечании пишет не модель, а корпус. Юридические требования документа задаются модели пачкой — одним запросом на 12 требований (`SNOSKA_CHECKS_CHECKS_PER_REQUEST`), у каждого — свои нормы; ответ — `{"verdicts": [...]}`, каждый вердикт проверяется отдельно, и заново спрашиваются только отклонённые, с указанием ошибки; после второй неудачи требование честно помечается «не выполнено». `uncertain` превращается в замечание «требует проверки юристом», `absent` — в «не найдено в документе».

**Запуск и прогресс.** Разобранная версия ставится на проверку в той же транзакции, что фиксирует разбор (outbox). Задача в воркере выполняет правила, затем модельные проверки параллельно (по числу слотов модели); каждый результат и счётчик прогресса сохраняются своей транзакцией, повторная доставка задачи продолжает с последнего сохранённого результата. Триггер на `check_runs` шлёт `NOTIFY`; API держит одно слушающее соединение на процесс и отдаёт прогресс клиенту как server-sent events (`/check-runs/{id}/events`), перечитывая запуск из базы под тенантом клиента — уведомление сообщает только, *какой* запуск изменился.

**Качество — на эталонном наборе.** `backend/demo/reference` — 14 документов, которые мы написали сами (политики, положение, согласия, договоры поручения, приказы; полные и с намеренными ошибками), и `labels.yaml`: какие проверки должны найти нарушение в каждом. `snoska checks benchmark` (`make benchmark`) разбирает и проверяет их так же, как продукт, но вне базы (векторы фрагментов — в памяти), сравнивает вердикты с разметкой и сохраняет точность и полноту по каждой проверке, семейству и способу, а также время разбора, правил и модели на каждом документе — в `backend/data/quality/benchmark.json` (его отдаёт `/v1/checks/quality` и показывает страница «Как мы проверяем») и в [`docs/quality.md`](quality.md). Нарушение — положительный класс; «требует проверки юристом» для полноты считается пропуском, невыполненные проверки в меры не входят и показываются отдельно. Метка для проверки, неприменимой к виду документа, останавливает замер. Тест гейта повторяет замер правил и сверяет его с сохранённым, поэтому опубликованные цифры всегда соответствуют коду; после изменения реестра замер перезапускают, а страница до этого помечает его как сделанный на прежних правилах. Юридические проверки измерены той же командой с подключённой моделью; замер не читает кэш ответов, чтобы время было временем модели, отказывается начинать, если сегодняшних запросов к модели не хватит, и ничего не сохраняет, если лимит кончился посередине. Кандидатов сравнивают пробными замерами (`--trial --model …`) на общих документах, выбранный публикуется (`snoska checks adopt`).

**Замечания и решения по ним.** Статусы: открыто, принято, отклонено, исправлено; принять или отклонить может юрист или владелец, отметить исправленным — и исполнитель (права ролей — реестр в домене). Изменение — с проверкой ревизии. При повторной проверке решение «принято/отклонено» переносится на то же замечание (та же проверка и тот же фрагмент), «исправлено» — нет: если замечание осталось, исправление не сработало.

## Модели — только через внешний API

**Решение владельца: локальный запуск нейросетей на машине запрещён** — ни языковых моделей, ни эмбеддингов. Модели подключаются только через внешний API: адаптер OpenAI-совместимого API (чат с ответом по JSON-схеме и эмбеддинги), провайдер, адреса, ключи, модели и размер векторов задаются конфигурацией (`SNOSKA_AI_PROVIDER`, `SNOSKA_LLM_*`, `SNOSKA_EMBEDDING_*`). Пока API не настроен (`none`), адаптеры на каждый вызов отвечают «модель не подключена»: детерминированные проверки работают, модельные записываются как невыполненные с кодом `model_not_configured`, интерфейс показывает это состояние. В тестах — детерминированные заменители по контракту портов (векторы из хеша текста, записанные ответы модели) без сети и моделей.

**Бесплатный тариф модели — 50 запросов в день, и продукт с этим живёт.** Четыре меры, все за портами:

- *пачки* — юридические требования документа идут одним-двумя запросами вместо одного на требование;
- *кэш ответов* (`model_completions`, `SNOSKA_LLM_CACHE_DAYS`) — ключ из первой модели цепочки, сообщений, схемы и параметров; название документа в запрос не входит, поэтому тот же текст в любой организации и повторная проверка стоят ноль запросов;
- *бюджет* в Redis, общий для API, воркера и CLI: темп в минуту и лимит в сутки по UTC (`SNOSKA_LLM_REQUESTS_PER_MINUTE`, `_PER_DAY`); запрос, который провайдер отклонил как перегруженный, возвращается в бюджет. Исчерпанный лимит — не ошибка проверки: правила выполняются, юридические требования получают код `model_daily_limit` и сами проверяются снова, когда лимит обновится (задача `checks.resume` раз в час); «Спросить норму» и консоль показывают остаток;
- *цепочка бесплатных моделей* (`SNOSKA_LLM_FALLBACK_MODELS`): перегруженная модель — две попытки, затем следующая; ответ, обрезанный по длине или не JSON, той же модели не повторяется. Платные модели — только решением владельца.

Модель выбрана по данным — пробными замерами на эталонном наборе ([quality.md](quality.md)): `nvidia/nemotron-3-super-120b-a12b:free` (точность 100 %, полнота 95 % на общих документах, 19,9 с на документ против 46,7 с у `nemotron-3-ultra`; `gemma-4-31b-it` на бесплатном доступе не ответила). Эмбеддинги — `baai/bge-m3`, 1024.

**Почему только с цитатой.** Модель без контекста на вопрос о сроке прекращения обработки после отзыва согласия ответила «не позднее трёх рабочих дней»; ч. 5 ст. 21 152-ФЗ говорит о тридцати днях. Поэтому ни ответ, ни замечание не принимаются без дословной цитаты из данного модели положения закона и фрагмента документа.

## Демо-стенд и лендинг

**Лендинг** — корень того же приложения Next.js (`/`) для гостей, вошедшие сразу попадают в свою организацию: один домен, одна сессия, одна дизайн-система, реальные экраны продукта в записях. Цифры на лендинге берутся из API (реестр проверок, последний замер качества, тарифы), видео записываются на стенде (`e2e/landing/record.mjs`). «Как мы проверяем» открыта без входа.

**Демо-вход в один клик** включается только настройкой `SNOSKA_DEMO_MODE` (по умолчанию выключен). Сервер входит выбранной ролью через отдельный клиент Keycloak `snoska-demo` (direct grant, секрет только у сервера) и открывает обычную сессию через тот же BFF. Выбрана *общая песочница с ночным сбросом*, а не отдельная копия на посетителя: копия на каждого — это провижининг организации в Keycloak и десятки документов на визит, а запросы к модели ограничены; общие организации с защищёнными учётными записями (роль и членство демо-входа изменить нельзя, `demo_account_protected`) и возвратом к сиду каждую ночь (`snoska demo nightly`, `SNOSKA_DEMO_RESET_HOUR`) дают честное «попробуйте сами» без утечки чужих данных. Сброс удаляет тенанта ролью-владельцем схемы (каскад от `organizations`, отдельно — append-only таблицы и задания outbox) и его файлы, затем сид применяется заново.

**`make demo-refresh`** обновляет всё, что зависит от модели: индекс корпуса, сброс стенда, перепроверку, замер качества, скриншоты вехи, записи лендинга и видео; каждый шаг ждёт воркер (`snoska checks wait`).

## Выбор технологий

**Очередь — Dramatiq + Redis.** Зрелая библиотека с надёжной доставкой (подтверждения, возврат незавершённых сообщений), ретраями с backoff, лимитами времени, middleware и асинхронными акторами. Celery тяжелее и слабее в asyncio; Arq в режиме поддержки; Taskiq моложе. Лицензия LGPL-3.0 — библиотека используется без изменений.

**PDF — pdfplumber (pdfminer.six) + pypdfium2 + Tesseract.** Даёт символы со шрифтами, кеглем и координатами — то, что нужно для проверок оформления на вехе 2, — а pypdfium2 быстро рендерит страницы для OCR. Docling тянет PyTorch и модели на гигабайты и неуместен при ограниченной памяти; его сильные стороны (layout-модели) покрываются эвристиками, которые мы контролируем.

**Модели — за портами `LanguageModel` и `Embedder`**, единственный рабочий адаптер — OpenAI-совместимый API (см. «Модели — только через внешний API»). Выбор конкретного провайдера и моделей — за владельцем; требования к ним: хороший русский, ответ по JSON-схеме (`response_format: json_schema`), мультиязычные эмбеддинги.

**Страницы входа — собственная тема Keycloak** (`infra/keycloak/themes/snoska`). Шаблоны FreeMarker на базе темы `base`: те же токены, что в приложении (копия `tokens.css` генерируется из исходника приложения, гейт проверяет её актуальность), IBM Plex из официальных пакетов IBM, иконки Tabler, обе темы — по выбору в приложении или по системной настройке. Keycloakify отклонён: он собирает тему из React через Maven и добавляет второй сборочный контур ради нескольких форм; собственная тема подключается каталогом, обновляется без пересборки и зависит только от стабильных переменных шаблонов Keycloak. Страницы, для которых нет своего шаблона, рендерятся шаблонами `base` в нашей разметке.

**Аутентификация — Keycloak, вход через сервер приложения (BFF).** Authorization Code + PKCE выполняет Next.js на сервере; токены хранятся в зашифрованной серверной сессии в Redis и не попадают в браузер; браузер обращается к API только через маршрут `/bff`, который подставляет токен. API проверяет подпись (JWKS с кешем по `kid`), издателя, аудиторию и срок действия.

## Фронтенд

Next.js 16 (App Router), TypeScript strict. Типы API генерируются из `backend/openapi.json` — ручных копий контрактов нет. Списки и документ рендерятся на сервере с первыми данными и продолжаются на клиенте (TanStack Query, гидрация). Собственная дизайн-система: токены (цвета для обеих тем объявлены один раз через `light-dark()`), компоненты на примитивах Radix, иконки Tabler; Stylelint запрещает литералы цветов и отступов вне токенов. Все тексты — в `messages/ru.json` (next-intl); коды реестров с точкой (`check.completed`) хранятся в каталоге с подчёркиванием.

**Оболочка и права.** Разделы организации — реестр навигации с правом на каждый раздел; группа «Организация» (участники, пространства, API-ключи, вебхуки, журнал, тариф) видна только тем, у кого есть права. Права документа и пространства приходят с сервера и действуют внутри своей области (`PermissionScope`); то, что относится к организации целиком (например, доступ к тарифу), проверяется по роли в организации. Консоль платформы — отдельная оболочка из тех же компонентов. Общие компоненты библиотеки (`shared/ui`): список записей, раздел страницы, страница и её главное действие, подтверждение с последствиями, переключатель, множественный выбор, поле с копированием, шкала использования, уведомление в строке, пары «название — значение», форма.

**Экран результата — документ со сносками.** Лист документа в центре, у каждого замечания — надстрочный номер в тексте и карточка на полях вровень с ним (раскладка без наложений: карточка, которой не хватает места, сдвигается вниз, выбранная встаёт точно к своему номеру); замечания о документе в целом занимают на полях по строке, пока их не откроют, и не отнимают место у сносок. Цвет пометки и карточки — серьёзность; фильтр по серьёзности и по решению. На телефоне и планшете поля открываются нижним листом из панели в зоне большого пальца. Ход проверки приходит событиями сервера (`EventSource` через BFF), отчёт обновляется не чаще раза в полторы секунды, остальной интерфейс не блокируется. Документ без замечаний называется «без замечаний», только если каждая применимая проверка дала вердикт; иначе — «проверено частично» (в списке) и прямая пометка, что не выполнено и почему (на экране результата).

## Наблюдаемость

Структурные JSON-логи (structlog) с `request_id`, пользователем, тенантом и `trace_id`; метрики Prometheus (`/api/metrics`, у воркера — порт 46302): запросы, задержки, задания и их длительность; трассировка OpenTelemetry включается настройкой (`SNOSKA_TRACING_EXPORTER=otlp`). Ошибки API — RFC 9457 с устойчивым `code`.
