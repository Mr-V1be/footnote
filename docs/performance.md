# Производительность

Нагрузочный тест API и время проверки с моделью. Замер от 3 октября 2026 г.

## Как запускали

- Сценарий — [`load/k6/snoska.js`](../load/k6/snoska.js), запуск `make load` (k6 1.3.0 в Docker-образе `grafana/k6`, в систему ничего не ставится, сеть хоста).
- Стенд разработки на одной машине: API — один процесс uvicorn (`FOOTNOTE_API_WORKERS=1`), воркер Dramatiq (2 потока), PostgreSQL 18 с pgvector, Redis, файлы на диске. Машина — 32 потока, 30 ГБ памяти, общая с другими задачами: цифры — нижняя граница, а не предел продукта.
- Клиент — интеграция по API-ключу: тест входит владельцем демо-организации через демо-клиент Keycloak, выпускает ключ на время прогона и отзывает его в конце.
- Перед прогоном стенд возвращается к сиду (`snoska demo reset`), после загрузок — `snoska checks wait`.
- Ответы модели для документов, которые уже проверялись, берутся из кэша: тест меряет продукт, а не внешнего провайдера. Время модели — отдельно, ниже.

Четыре потока одновременно, каждый — с постоянной частотой запросов:

| Поток | Что делает | Частота |
| --- | --- | ---: |
| list | список документов пространства | 30 в секунду |
| report | последняя проверка документа со всеми замечаниями | 10 в секунду |
| upload | загрузка DOCX; воркер разбирает и проверяет его | 1 в секунду |
| check | запрос проверки и её ход по SSE до события `end` | 1 в 2 секунды |

## Рабочая нагрузка: 60 секунд, 42 запроса в секунду

2 530 запросов, ошибок — 0.

| Запрос | Медиана | p95 | Максимум |
| --- | ---: | ---: | ---: |
| Список документов | 15 мс | 24 мс | 258 мс |
| Отчёт проверки | 23 мс | 35 мс | 220 мс |
| Загрузка DOCX | 38 мс | 76 мс | 154 мс |
| Запрос проверки | 29 мс | 55 мс | 73 мс |
| Все запросы | 17 мс | 36 мс | 1,09 с |

Проверка целиком:

| Что | Среднее | p95 | Максимум |
| --- | ---: | ---: | ---: |
| От запроса проверки до события `end` в SSE (31 проверка) | 0,49 с | 0,92 с | 1,12 с |
| От загрузки до готовой проверки в воркере (61 документ, по базе) | 0,44 с | 0,80 с | 1,43 с |

Все пороги сценария выполнены: p95 списка < 500 мс, отчёта < 800 мс, загрузки < 1,5 с, проверки до `end` < 30 с, ошибок < 1 %.

## Пик: цель 200 запросов в секунду, 30 секунд

Частоты подняты в пять раз (`LIST_RATE=150 REPORT_RATE=50 UPLOAD_RATE=2 CHECK_RATE=2`).

- Достигнуто 124 запроса в секунду; 2 017 итераций k6 не успел начать — один процесс API насыщен.
- p95 всех запросов — 6,8 с, загрузки — 10,8 с; проверка до `end` — p95 11,5 с.
- Ошибок — 1 из 4 104.

Вывод: один процесс API держит около сотни запросов в секунду с задержками в десятки миллисекунд; дальше растёт очередь, но запросы не теряются. Масштабирование — процессы API (`FOOTNOTE_API_WORKERS`, по ядру на процесс) и потоки или реплики воркера; в продакшен-сборке API запускается с несколькими процессами (см. [deploy.md](deploy.md)).

## Время проверки с моделью

Из замера на эталонном наборе ([quality.md](quality.md)): модель `nvidia/nemotron-3-super-120b-a12b:free`, ответы не из кэша, юридические требования документа — одним или двумя запросами.

| Что | Время |
| --- | ---: |
| Типовая политика, 8 страниц | 45,4 с |
| Среднее на документ набора (14 документов) | 10,1 с |
| Медиана | 6,2 с |
| Разбор и правила оформления | десятки миллисекунд, скан — 1,4 с |

Ограничение бесплатного тарифа модели — 50 запросов в день. Документ стоит 1–2 запроса, повторная проверка того же текста — ноль (кэш). Когда дневной лимит исчерпан, правила оформления выполняются как обычно, юридические требования ждут и проверяются сами после обновления лимита (задача раз в час); вопрос к норме честно говорит о лимите.

## Как повторить

```bash
make up && make api && make worker      # стенд, FOOTNOTE_DEMO_MODE=true
cd backend && uv run snoska demo reset && uv run snoska checks wait && cd ..
make load                               # 60 секунд, сводка в .run/k6/summary.json
DURATION=30s LIST_RATE=150 REPORT_RATE=50 UPLOAD_RATE=2 CHECK_RATE=2 scripts/load-test.sh
```

Загруженные тестом копии остаются в демо-организации до ночного сброса стенда.
