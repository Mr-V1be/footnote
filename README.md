# Сноска

Сервис проверки документов на соответствие 152-ФЗ «О персональных данных» и правилам оформления (ГОСТ Р 7.0.97-2016). К каждому замечанию — «сноска»: точная ссылка на статью, часть и пункт нормы с цитатой.

Текущее состояние — веха 2 «Проверка». Веха 1 дала организации и роли, изоляцию тенантов, загрузку DOCX и PDF (включая сканы) с разбором структуры, корпус 152-ФЗ, дизайн-систему, список и просмотр документов. Веха 2 — сама проверка: реестр из 43 проверок (оформление по ГОСТ Р 7.0.97-2016 — правилами, требования 152-ФЗ — языковой моделью только с цитатой найденного фрагмента), результат как документ со сносками и карточками на полях, решения по замечаниям (принято, отклонено, исправлено), ход проверки в реальном времени, страница «Как мы проверяем» с точностью и полнотой на эталонном наборе.

## Быстрый старт

Нужны Docker с Compose, Python 3.13 и [uv](https://docs.astral.sh/uv/), Node 24 и pnpm 10, Tesseract с русским языком (`tesseract-ocr-rus`). Для пересборки демо-документов — LibreOffice. Нейросети на машине не запускаются: языковая модель и эмбеддинги подключаются только через внешний OpenAI-совместимый API.

```bash
make env            # .env со случайными секретами
make up             # PostgreSQL + pgvector, Redis, Keycloak, Mailpit
cd backend && uv sync && cd ..
cd frontend && pnpm install && cd ..
make migrate        # схема БД
make corpus         # 152-ФЗ из снимка портала
make seed           # демо-организации, участники и документы

# в отдельных терминалах
make api            # http://127.0.0.1:46301
make worker         # фоновые задачи и отправка outbox
make web            # http://localhost:46300
```

`make stop` останавливает контейнеры. `make recheck` заново проверяет последние версии всех документов (после изменения реестра проверок), `make benchmark` измеряет проверки на эталонном наборе и обновляет [`docs/quality.md`](docs/quality.md).

### Модели

Проверки оформления работают сразу. Юридические проверки по 152-ФЗ выполняет языковая модель через внешний API: укажите в `.env` `SNOSKA_AI_PROVIDER=openai_compatible`, адрес и ключ (`SNOSKA_LLM_BASE_URL`, `SNOSKA_LLM_API_KEY`), модели (`SNOSKA_LLM_MODEL`, `SNOSKA_EMBEDDING_MODEL`) и размер векторов (`SNOSKA_EMBEDDING_DIMENSIONS`), затем выполните `make index` — корпус получит векторы новой модели. Без этого юридические проверки отмечаются как «модель не подключена».

### Демо-доступы

Учётные записи и пароли — в [`backend/demo/seed.yaml`](backend/demo/seed.yaml). Организации:

- **ООО «Полярная звезда»** — владелец, юрист, исполнитель и наблюдатель (без права загрузки); пять документов, у положения две версии, приказ — скан.
- **АО «Речной порт»** — владелец и юрист; два документа.
- **ООО «Заря»** — владелец и юрист; пять черновиков с типичными ошибками из эталонного набора: на них видны замечания.
- **ИП Соколова** — новая организация без документов.
- Суперадмин платформы — `operator@snoska.example`.

Вход — через Keycloak со своей темой страниц входа (форма в два шага: e-mail, затем пароль). Realm импортируется при первом запуске Keycloak; чтобы применить изменения `infra/keycloak/realm-snoska.json` к уже созданному realm, удалите его в консоли администратора и перезапустите контейнер — `make seed` заново создаст организации и участников.

## Архитектура

```
backend/src/snoska/
  domain/          модель без ввода-вывода: тенанты и роли, документы, корпус норм,
                   проверки (реестр, правила оформления, замечания, метрики качества)
  ports/           контракты: репозитории, unit of work, хранилище, очередь, парсеры,
                   OCR, LanguageModel, Embedder, источники корпуса, identity
  application/     сценарии: загрузка, разбор, запросы, корпус, движок проверок,
                   юридические проверки с опорой на цитаты, замер качества
  infrastructure/  адаптеры: PostgreSQL (RLS), Dramatiq/Redis, python-docx, pdfplumber,
                   Tesseract, OpenAI-совместимый API моделей, Keycloak, pravo.gov.ru
  bootstrap/       корень композиции и настройки
  api/ worker/ cli/  точки входа
frontend/src/
  shared/          дизайн-система (токены, компоненты), клиент API, i18n
  features/        оболочка, документы (список, загрузка, просмотр), результат проверки,
                   замечания на полях, «Как мы проверяем»
  server/          BFF: сессии, OIDC, обращения к API
  app/             маршруты Next.js
```

Зависимости направлены внутрь; это проверяет `import-linter`. Подробности и обоснования решений — в [`docs/architecture.md`](docs/architecture.md).

## Качество

`scripts/gate.sh` — те же проверки, что в CI: размер файлов (≤ 700 строк) и папок (≤ 15 файлов исходников), ruff, mypy `--strict`, контракты импортов, актуальность OpenAPI, pytest (включая интеграционные тесты изоляции тенантов на PostgreSQL), tsc, ESLint, Stylelint (запрет литералов цветов и отступов вне токенов), Prettier.

Скриншоты всех экранов вехи (390×844, 768×1024, 1280×800, светлая и тёмная тема) — `docs/screenshots/m2/` (веха 1 — `docs/screenshots/m1/`, исправления по её приёмке «до/после» — `docs/screenshots/m2/fixes/`), снимаются `cd frontend && pnpm screenshots` (`MILESTONE=m1` — набор вехи 1).

Качество проверок на эталонном наборе — [`docs/quality.md`](docs/quality.md).
